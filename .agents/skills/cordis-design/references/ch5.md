# 5. Implementation and Case Study

## Summary
This chapter grounds the formal models of Section 3 in a working system, Cordis, and closes the paper's
argument with production evidence. It presents Cordis as a meta-framework of spatiotemporal
composability: it prescribes no application domain, only universal dynamic-composition semantics, built
in three tiers. The core library (5.1) realizes the effect and coeffect calculi directly as
`ctx.effect`, `ctx.get`/`ctx.set`/`ctx.isolate`/`ctx.intercept`, and the fiber lifecycle machine
(`ctx.use`, `refresh`, `reload`, `unload`). The component loader (5.2) layers a declarative
configuration on top, giving orchestrators persistent, diffable entries that the loader reconciles into
fiber operations, plus hot module replacement (HMR) that reuses the same revertible-effect machinery to
swap source modules without developer-annotated acceptance boundaries. The case study (5.3) validates the
model against Koishi, a four-year-old, 4000-plugin production chatbot framework, arguing the model is both
expressive (a whole production system rides on the primitives) and general (it fixes only how effects and
coeffects compose, not what they mean, so the same core powers a server runtime and, unmodified, a browser
console). Throughout, the chapter repeatedly ties implementation choices back to specific numbered results
from Sections 3 and 4 (Theorems 68, 70, 71, 73, 80; Lemmas 59, 77; Corollary 69; Definitions 18, 22, 23,
25, 27, 46, 49, 52, 53, 74, 76, 81), showing each engineering decision — LIFO disposal, marking UNLOADING
before scheduling inverses, comparing by provider uid rather than by value, waiting on dependents ahead of
recovery, delimiter tags for realm reassignment — is not incidental but forced by, or a direct realization
of, the metatheory. This chapter is the paper's proof that the calculus is implementable efficiently and
that the implementation's correctness properties (no half-torn-down state, order-independent reconciliation
that converges, transactional HMR) are consequences of theorems proved earlier rather than separately
re-argued engineering claims.

## Section-by-Section

### 5. Implementation and Case Study (chapter opening / configuration revision)
- Cordis is described as a meta-framework: it supplies universal dynamic composition semantics and targets no specific application domain (unlike ORM or UI frameworks), and is layered into three tiers — core library (5.1), component loader (5.2), and application frameworks such as Koishi (5.3).
- Configuration is carried inside the effect function `e`: two components differing only in their bound payload are two distinct components under Definition 48, since instantiation binds the payload into the effect function the fiber runs.
- A declarative revision of a running fiber (new configuration, reassigned realms, or disable/re-enable) is implemented as a composite of the core rules: disabling alone is an O-Retire, while every other revision retires the fiber, lets the lifecycle deactivate it, removes the entry (children before parent, as O-Remove requires), and reinserts the fiber at the same name — potentially with a reissued name, since Section 4.3.1 guarantees no stale committed view can name a removed fiber.
- Dependents require no special-casing on revision: the guard on L-Unload already orders withdrawal after the deactivations it causes, and target-view comparison reactivates each dependent once the reinserted fiber supplies the keys again.
- Re-enablement is implemented as the full composite rather than as a single rule resetting `τ` to `⊥`, for two theorem-driven reasons: Theorem 80 depends on a fiber that an accumulator retires staying retired (Lemma 59(5)), and Definition 53 reads no parent pointer, so un-retiring a fiber after its creator's accumulator has already run would activate it with its creator gone.
- The implementation therefore keeps entry-versus-fiber as two distinct identities: the entry is what survives revision, while the fiber is the identity of one particular enablement; a re-enabled entry always instantiates a fresh fiber.
- Holding the composite to its theorem-guaranteed endpoint (Theorem 80: the system quiesces exactly where loading the revised configuration from scratch would) is what licenses the loader's "shorter routes" — e.g., handing a new payload to a component that reloads only on material change, or moving a realm without reloading its provider — because those shortcuts are justified by reaching the same endpoint, not by mimicking the same steps.

### 5.1. Core Library
- Table 2 gives the theory-to-implementation correspondence used throughout the section: `Γ∞` is `ctx` (the first-class context); a fiber `⟨d, p, e, π, σ, τ, θ⟩` is the runtime `fiber` object; `θ` is `fiber.state` (LOADING realized as "Reloading", FAILED carrying the Section 4.4 error outcome); the accumulator `g`/`recover` is `fiber.dispose`; the committed view `ω` is `fiber.committed`; `target(γ,n)` is `fiber.target` (recomputed by `refresh`, with `⊥` realized as INACTIVE); and `Future`/inertia is `fiber.inertia`, the handle to the in-flight transition.
- Rule correspondences: O-Insert/O-Retire (Definition 52) map to `ctx.use` and the inverse of its callback (Algorithm 4); O-Remove is the fiber dropped from the runtime with its uid cleared; L-Begin/L-Iter/L-Finish map to `execute`'s iteration loop (Algorithm 1); L-Divert maps to the guard failing at an iteration boundary or reload chaining into unload; L-Leave maps to `refresh` marking the fiber UNLOADING; L-Unload maps to `unload` and its inertial chaining (Algorithm 5), with the guard on L-Unload realized as `unload` awaiting notified dependents (Line 25).
- The library is built bottom-up across four subsections: 5.1.1 realizes revertible effects (the sole mutation primitive), 5.1.2 realizes reactive coeffects over that store, 5.1.3 composes both into the component lifecycle, and 5.1.4 exposes context-level read access built on the former three.
- The notation `ctx[@@name]` denotes symbol-keyed access to an opaque slot on the context (framework-internal), distinct from string-keyed map indexing, and is used for the three coeffect tables introduced in 5.1.2.

### 5.1.1. Effect Tracking
- Every context mutation in Cordis funnels through one primitive, `ctx.effect`: coeffect provision, component instantiation, and all other context-mutating operations reduce to a `ctx.effect` call, so every operation performed through the context is automatically tracked and reverted on unload.
- Operationally, `ctx.effect` realizes `effect^iter_Γ` (Definition 18): it lifts a callback of type `ℑΓ` to `ℑ∂Γ`, yielding a dispose closure that reverts the effect when invoked; Cordis accepts both `𝔈Γ` and `ℑΓ` through this one operation via ad-hoc polymorphism, treating a plain effect function as the degenerate iterator yielding a single inverse.
- The runtime does not check the witness carried by `𝔈*Γ`: that a supplied inverse actually reverts its accompanying effect is an obligation on the component author, not a property the runtime verifies — Theorem 68 is where the calculus appeals to that witness, and Section 6.1 delimits the obligation; the coeffect witness of Definition 46 (commutativity of published operations) is unchecked in the same way, discharged instead by the representation choice of Section 3.4.2.
- Algorithm 1 (`execute`) drives a callback as an effect iterator, folding each step's yielded inverse into a single composite via `f ∘ g` (run `f` after `g`, with `id` as no-op), so prepending each new inverse yields LIFO recovery; before every step it consults a caller-supplied `guard`, and once the guard trips, iteration stops and only inverses accumulated so far remain — this realizes the step-boundary interruption of Section 4.2.2, where the `Maybe(ℑ)` continuation is realized by the iterator's `done` flag together with `guard`.
- `ctx.effect` wraps `execute` and adds self-disposal (an `armed` flag reported to the guard; the returned `dispose` flips it false, halting any in-flight iteration and ensuring recovery fires at most once — firing twice would apply an inverse at a state nothing produced) and parent composition (the returned `dispose` is prepended to the enclosing context's `ctx.dispose`, so a child effect's inverse is itself an effect on the parent — the recursive structure of `∂²Γ`).
- The component level (5.1.3) reuses the same `execute` engine but supplies a different guard, one that tests the stability of `fiber.target` rather than the `armed` flag.

### 5.1.2. Coeffect Operations
- All coeffect operations act on three symbol-keyed context slots: `@@store` (the value store `σ : (r:R) ⇀ 𝒱_r` from realm symbols to typed values), `@@isolate` (the realm table `ρ : Map(K,R)` from coeffect keys to realm symbols), and `@@intercept` (the interception table `ι : (k:K) → ℳ_k` assigning each key its metadata).
- `@@store` and `@@isolate` compose into the two-layer resolution `k → ρ(k) → σ(ρ(k))`: `ctx.get(key)` (Algorithm 2) reads the realm symbol from `@@isolate` and then the bound value from `@@store`; the `ρ` indirection lets isolation redirect a key to an independent binding, while `@@intercept` is consulted only at access time and adjusts how a binding is used rather than what it resolves to.
- Since `set(k,v)` has type `𝔈Σ`, `ctx.set` (Algorithm 2) is implemented as a `ctx.effect` call and inherits automatic tracking/recovery for free; both the install callback and its returned dispose invoke `notify` to propagate the change.
- Algorithm 3 (`notify`) tests, for every live fiber, whether a changed key appears in `fiber.inject` and resolves to the same realm as the change; if so it calls `refresh` to re-evaluate that fiber and collects it into the returned set so a caller can wait on it — this realizes the reactive classification of Definition 22, where a satisfaction-flipping change activates/deactivates a fiber and `refresh`'s idempotence renders a neutral change harmless.
- A binding counts as available to a dependent only while its providing fiber is ACTIVE (the "provided by" relation of Definition 53), so `refresh` resolves each declared key against an active provider rather than the store alone; this is what makes a withdrawal visible one step early: once a provider enters UNLOADING it has already stopped "providing," so dependents recompute an unsatisfied target view and begin their own teardown while the provider's bindings are still physically in place.
- `ctx.isolate(key, realm)` (realizing `isolate`, Definition 25) derives a child context overriding `ρ` at `key` with either a supplied realm or a freshly generated symbol, so recovery is implicit — discarding the child context suffices, with no explicit inverse needed; `ctx.intercept(key, metadata)` (realizing `intercept`, Definition 27) similarly derives a child context but merges new metadata into `ι`, with the new metadata taking priority over what the context already carries.

### 5.1.3. Component Lifecycle
- A component is instantiated as a fiber by `ctx.use`, giving the fiber operational meaning as the inertial state machine of Section 4.4; two driving fields are `fiber.parent` (the parent context, forming the recursive `Γ∞` hierarchy of 3.3.1) and `fiber.inertia` (a handle to the in-flight async transition, or null if idle).
- Algorithm 4 (`use`) instantiates a component: it pairs `component.inject` (`d`) with `component.apply`, binds config into `fiber.apply` (the config-applied effect function `e`), and registers a `callback` as a tracked parent effect whose forward action calls `refresh` (initiating the child's lifecycle) and whose reverse action forces `fiber.target ← ⊥` and calls `unload` — this realizes the instantiation primitive of Definition 52, with `callback` as O-Insert and its returned closure as O-Retire, so unloading a parent automatically cascades to its children as an ordinary tracked effect.
- Algorithm 5 realizes the Section 4.4 inertial state machine using two auxiliary lookups: `resolve(inject)` (bindings the declared keys currently resolve to) and `provided(fiber)` (keys this fiber installed); `refresh` recomputes `fiber.target` and, only if the fiber is not mid-transition, starts `reload` (target ≠ ⊥) or `unload` (target = ⊥) as a concurrent task.
- `reload` records the target (`target0`), commits the resolved view into `fiber.committed` at Line 14 (committing before running `apply`), runs `execute(fiber.apply, guard)` where the guard checks `fiber.target = target0` at each iteration boundary, and on completion either enters ACTIVE and calls `notify` (if the target still matches) or chains into `unload` regardless of whether the new target is `⊥` or a different provider set.
- `unload` first awaits every dependent notified via `notify(fiber.ctx, provided(fiber))` reaching completion (Line 25, "drain dependents"), then awaits `fiber.dispose()` in LIFO order, clears `fiber.committed`, and either enters INACTIVE or chains into `reload`; this mutual recursion between `reload` and `unload` implements the inertial property that a started transition runs to completion before any new target change is acted on.
- `fiber.target` is a digest of `target(γ,n)` (Definition 53) built by resolving each declared key against the current store and tupling in the *uid* of the providing fiber rather than the value; because a uid is drawn fresh and never reused, a replaced provider can never be mistaken for its replacement even when both provide equal values, and this identity-by-uid comparison is exactly what makes a single equality check against the recorded target sufficient — consequently, a provider that overwrites its own binding in place is not observed as a change (a component must withdraw and reinstall to propagate a replacement).
- The algorithm operates at two levels: transition-level (reload/unload check the target only at completion, enabling inertial chaining across transitions — corresponding to Section 4.4's inter-transition chaining) and iteration-level (Algorithm 1's `execute` checks the target at every iteration boundary, enabling partial rollback within a single transition — corresponding to the intra-transition staleness check Theorem 71 rests on).
- The coeffect ordering of Theorem 70 is realized by exactly three placements: `reload` commits the resolved view at Line 14 and `unload` discards it only after every inverse has run (so a loaded fiber reads consistent bindings throughout, including during its own teardown); `refresh` marks the fiber UNLOADING at Line 10 before the transition task is even created (the L-Leave step — the fiber stops providing before any of its inverses is scheduled); and `unload` waits at Line 25, ahead of the whole recovery (not inside any individual inverse, since `fiber.dispose` runs its effects concurrently and a wait nested inside one inverse would leave the rest unordered), for every notified dependent to reach INACTIVE — this is the guard on L-Unload, and termination follows Theorem 73 since a fiber only waits on dependents that have already become unsatisfiable, with the provider graph traversed on demand rather than pre-analyzed.

### 5.1.4. Context Access
- On top of the reflective API (`ctx.set`/`ctx.get`, both keyed by name, from 5.1.2), Cordis layers property access: a component reads a coeffect as `ctx[key]`, mediated in TypeScript by a Proxy `get` trap, realized by Algorithm 6 (`resolve`).
- Algorithm 6 walks the fiber chain upward from the accessing context: at the first fiber whose `committed` view binds `key`, the access is authorized and that binding returned; if the walk reaches a fiber that declares `key` in its `inject` without having committed it, the fiber is not loaded and access fails (`INACTIVE_ACCESS`); if it reaches the root with no declaration at all, access is rejected (`UNDECLARED_ACCESS`).
- This differs materially from bare `ctx.get`: `ctx.get(key)` is an unconditional store lookup that returns the bound value or nothing and never fails, whereas the proxy resolves against the *accessing fiber's own committed view* and enforces the declared coeffect specification `d` at the point of use.
- Reading the committed view rather than the live store is precisely what Theorem 70 rests on, since it is what keeps a dependency readable to a component whose own teardown was triggered by that dependency's disappearance (the view stays frozen until the fiber's own inverses have all run).
- The runtime check happens at access time, but because `d` is declared statically, the same violation is in principle detectable at compile time by resolving each `ctx[key]` against the declared `d` before execution; Section 6.4 discusses host-language type-level dependency declarations and compile-time metaprogramming as a way to carry this out.

### 5.2. Component Loader
- The core library gives component developers imperative primitives (`ctx.effect`, `ctx.use`, `ctx.set`) for dynamic composition; a separate concern belongs to application orchestrators who assemble pre-existing components into a running system and must adjust that composition over its lifetime.
- The component loader addresses this by adding a declarative configuration layer: the orchestrator specifies the desired composition as a persistent data structure, and the loader translates changes to that specification into the corresponding imperative fiber operations.

### 5.2.1. Declarative Configuration
- Definition 81 defines an entry as declaring a single fiber and recording six fields: `id` (stable reconciliation key within its group's child list), `url` (the component module's URL), `isolate` (isolation annotation), `intercept` (interception annotation), `config` (the payload bound into `apply`), and `disabled` (administrative on/off flag).
- An entry is a faithful specification because it supplies exactly the support set of Definition 74 (`τ`, `π`, `d`, `p`, and nothing else): `disabled` gives `τ`, the entry's tree position gives `π`, and `url` selects the component that declares `d` and `p`; the fields the support set omits are runtime state that instantiation doesn't need either, and Lemma 77 identifies this support set with the Active fibers of a quiescent state as far as each component installs every key it declares (Definition 76).
- Entries form a configuration tree, the authoritative record of what the system loads; `@cordisjs/group` takes a list of child entries as its `config` and loads them as a subgroup, and `@cordisjs/include` loads an external YAML/JSON configuration file and grafts its entries as a nested subtree — both are ordinary components resting on the Definition 52 instantiation primitive (Algorithm 4), so nested trees stay within the calculus and all the section's results hold of them.
- Reconciliation is incremental (never a full teardown/rebuild) and is justified by four cited results: Theorem 80 (the quiescent state depends only on the final configuration, regardless of the order or path of instantiations/retirements taken to reach it, as long as each declaring component installs every key it declares per Definition 76); Theorem 73 (the system provably quiesces, so a reconciliation is complete once its instantiations/retirements are issued); Corollary 69 (a departing fiber's contribution to the state becomes nothing, so rebuilding one entry cleanly withdraws just its own installations); and Theorem 70 (entries can be instantiated together with no orchestrator-imposed load order, since a fiber with unsatisfied declared keys simply waits at L-Begin and a fiber whose provider leaves is deactivated ahead of it — so module loading can proceed concurrently).
- The loader dispatches per changed field with the least disruptive operation: `id`/`url` changes rebuild the entry (identity or component changed); `isolate` changes reassign realms via Algorithm 7; `intercept` changes update in place (consulted only at read time, no reload needed); `config` changes are handed to the component itself, which typically diffs against the previous payload and reloads only on material change (a `group` entry's config is its child-entry list, so updates apply as a keyed diff over child ids, and updating a surviving child recurses back into this same per-field dispatch); `disabled` changes unload the fiber (set) or reload it (cleared).
- Because a realm may move an entry between groups at runtime, the loader manages realms beyond the core's static child-context override: `isolate: true` selects a local realm private to the entry (tagged by its id, travels with it); `isolate: "someString"` selects a global realm shared by every entry naming that string (so a moved entry changes which entries it shares a binding with, not which realm it belongs to); an unused realm is discarded once no entry names it.
- Algorithm 7 (`patch_isolation`) reassigns realms using per-key delimiter symbols `δ_k`: each context stores a freshly generated tag under `δ_k` on isolation reassignment, and since the tag is inherited by descendants, a context's tag equals the provider's tag exactly when both were derived within the same isolate scope for `k` — this "own" predicate (equation 64: `γ'[δ_k] = d1 ⟺ γ' is derived from the entry's context`) determines which side of a realm move a given dependent tracks, so a dependent's visibility of the binding is unchanged when own agrees between it and the provider, and changes (gain/loses the binding) exactly when own separates them; the algorithm computes this via `affected` and calls `notify` with this predicate in place of Algorithm 3's plain realm-equality test.

### 5.2.2. Hot Module Replacement
- HMR applies the revertible-effect pattern at the module level: when source files change (typically in development), affected modules are replaced in place without restarting the process; because a fiber already bounds all of a component's effects and coeffects, replacing a module reduces to disposing the old fiber (which recovers everything installed) and instantiating a new fiber from the reloaded module — so Cordis HMR needs no developer-annotated acceptance boundaries, unlike Webpack or Vite HMR.
- The `@cordisjs/hmr` component runs three phases: (1) module classification, (2) stale-entry detection, (3) transactional reload.
- Phase 1, Algorithm 8 (`classify`), takes the stashed set (files changed since last reload) and externals set (modules that force a full restart) and computes a fixed point over the dependency subgraph: a module is `accepted` once one of its imports is accepted, `declined` once all of its imports are declined, and any module left undecided (e.g., stuck in an import cycle) defaults to `declined`.
- Phase 2, Algorithm 9 (`detect`), walks each entry's dependency tree via `get_dependencies` (which stops traversal at `declined` boundaries) and marks an entry stale exactly when its tree intersects `accepted`; a stale entry's whole tree is then folded back into `accepted`, propagating invalidation to every stale module along it for the next phase.
- Phase 3, Algorithm 10 (`reload`), invalidates the accepted modules' module-system caches (backing each removed module up for potential rollback), then for each stale entry disposes its old fiber and instantiates a fresh one via `ctx.use(import(entry.url), entry.config)`; on any import failure (e.g. a syntax error) the caches are restored and every stale entry is rebuilt from its backed-up previous module, undoing the swaps already made.
- This gives a transactional guarantee: the system never enters a half-reloaded state, because a failed reload restores caches and reconstructs every stale entry from its backup rather than leaving some entries on new modules and others on old ones.

### 5.3. Case Study: Koishi
- Koishi is an open-source chatbot application framework built on Cordis, with over four years of development and more than 4000 community-contributed plugins spanning IM adapters, database drivers, admin consoles, and end-user features — its scale and diversity serve as a production-scale validation of Cordis's dynamic composability.
- Koishi's server runs every feature as a plugin over the Section 5.1 context primitives, with Koishi itself contributing only chatbot-domain vocabulary; its web console is described as a second, independent Cordis application composing browser/UI primitives instead of server primitives, run entirely on the same core model.
- These two disparate deployments are used to establish two properties of the Section 3 model: (1) expressiveness — the primitives alone suffice to carry a complete production system, with the host framework supplying only domain vocabulary; (2) generality — the model fixes only how effects and coeffects compose while leaving their meaning to the application, presupposing neither a specific domain nor a specific runtime.
- The chapter contrasts this with the plugin systems surveyed in Section 1.2.1, which the paper says cannot unload an individual extension's effects without restarting the extension (the sentence is truncated at the file's end, page 69, so the chapter's final point about "temporal composability without cognitive overhead" is not fully captured in the extracted text).
- Footnotes clarify scope: Koishi currently runs on Cordis v3, while the paper itself presents Cordis v4 (which refines the effect/coeffect semantics and redesigns the loader, though the core compositional model is shared across both versions); and Koishi's own terminology calls the formalized "component" concept a "plugin."

## Relevance to an Agent Harness

- Plugin/module unload should be modeled as running one composed LIFO inverse (`fiber.dispose`) built purely from tracked effects, rather than as ad hoc teardown code, so unloading a component is guaranteed complete as long as every mutation went through the single tracked-effect primitive.
- Dependency-driven reactivation (a plugin providing a capability another plugin depends on) should compare providers by a stable, never-reused instance id rather than by value equality, since identity comparison is what lets the harness detect "my provider was replaced" even when the replacement exposes an identical-looking value.
- Hot module replacement can be implemented without asking plugin authors to declare "accept" boundaries (as Webpack/Vite HMR requires) if the framework already tracks every effect a module performs through one primitive — disposing the old instance and reinstantiating from the new module suffices, which is a strong simplification for a harness aiming for transparent hot-reload of plugins.
- A configuration-diffing loader that dispatches per changed field (identity/url → rebuild, isolation → realm reassignment, metadata → in-place update, payload → let the component itself decide via diffing, enabled flag → unload/reload) minimizes disruption on every config change, and doing so is sound specifically because the target system state is a pure function of the final configuration (independent of the order of operations used to reach it) — a harness config-reload path should aim for the same order-independence property before relying on incremental reconciliation.
- Realm/scope reassignment at runtime (e.g., moving a plugin between sandboxes or dependency-injection scopes without a full reload) is implementable via a per-key "provenance tag" pattern (delimiters) that determines whether a given consumer moves with the provider or stays behind, letting isolation scopes be mutable at runtime rather than fixed at instantiation.
- Multi-step reload/unload operations that can fail partway (e.g., HMR reimporting a broken module) should use a backup-and-restore transactional pattern: snapshot the previous working state before swapping, and on any failure roll every affected unit back from its snapshot rather than leaving a mix of old and new state.
- Dependent notification during unload should happen before the actual teardown is scheduled (mark "no longer providing" first, then let dependents observe an unsatisfied state and begin their own teardown, and only then run the actual disposal inverses) — this ordering prevents dependents from reading a binding that is about to disappear.
- A wait for dependent shutdown during unload must sit ahead of the entire recovery step (not nested inside one of several concurrently-run inverses), because nesting the wait would leave the other concurrent inverses unordered relative to it.
- Load-time dependencies between plugins need no orchestrator-imposed ordering if a plugin with an unsatisfied dependency simply waits (blocks activation) rather than erroring, and a plugin whose dependency disappears is deactivated ahead of it automatically — this allows concurrent module loading, which is where most of a large plugin-set's startup time is actually spent.
- Property-style access to shared/injected state (`ctx[key]`) should resolve against the accessing component's own frozen/committed view of its dependencies rather than a live global store, so a component's dependency stays consistently readable throughout its own teardown even after the underlying provider begins withdrawing.

## Open Questions and Limitations

- The chapter explicitly states that whether an inverse actually reverts its accompanying effect is *not* checked by the runtime — it is an unenforced obligation on the component author, and the paper defers full treatment of this obligation to Section 6.1 (outside this chapter's scope).
- Similarly, whether a coeffect's published operations actually commute (the witness of Definition 46) is unchecked by the runtime; it is discharged only by a representation choice made in Section 3.4.2, not verified at runtime in Section 5.
- The static/dynamic mismatch in context access is flagged but not solved here: `ctx[key]` violations of the declared coeffect specification are caught only at runtime (point-of-access), even though the specification is declared statically and could in principle be checked at compile time; the chapter defers the actual mechanism for compile-time checking to Section 6.4 and host-language type-level metaprogramming.
- Reconciliation soundness (Theorem 80) is explicitly conditioned on Definition 76 — components installing every key they declare; the chapter notes that a component whose behavior differs (declares a key but installs it only under some configurations) is still reconcilable, but then "the set of loaded components answers to those configurations as well," i.e., a caveat rather than a fully general guarantee.
- The extracted text cuts off mid-argument at the end of page 69 (chapter/section end) during the discussion of "Temporal composability without cognitive overhead," so the chapter's full comparison against the Section 1.2.1 survey of other plugin systems is incomplete in this excerpt — the final sentence describing why other systems cannot unload without restarting is truncated.
- The case study is presented as validating expressiveness and generality but is scoped to one framework family (Koishi, server + web console) and one host language (TypeScript); the chapter does not claim broader empirical validation (e.g., performance benchmarks, comparative measurements against other plugin systems) beyond the plugin-count/longevity anecdote.
- A footnote acknowledges Koishi currently runs on Cordis v3 while the chapter documents Cordis v4's refined effect/coeffect semantics and redesigned loader — so the production evidence (4000+ plugins) technically validates the earlier version's compositional model, with the paper asserting but not independently demonstrating that the core compositional model is "shared across both versions."
